Candidate and job matching for recruiters

Shortlist architecture

The same person and the same job are described differently, at different times, by sources of different authority. So every fact is stored with its source, date and exact words. Explicit rules run over those facts. Each piece of work is tied to the thing that changed, never to the size of the database.

What is kept, and what is computed

This split is what makes the rest of the design safe. Only two things are the record. Everything a recruiter sees is computed from them and can be thrown away.

Six rules that keep it correct across machines

  1. One person, one worker. Identity is settled before routing, on an index of emails and explicit references, so two records of one person always reach the same place.
  2. Unknown is not "no". Only a stated, different profession sets a person aside. People with no stated profession stay in every worker's pool.
  3. Order per person and per job. A late arrival is still placed correctly, because every fact carries its own date.
  4. An event applied twice changes nothing. Events carry an id; a row is written by its key.
  5. A row, its change message and its outbox entry are written together, so a recruiter is never told about a move that was not saved.
  6. Every row records the settings version that produced it. A rebuild writes the new version beside the old one and switches when complete.

Rules 3 and 4 hold in the code today. Rules 1, 2, 5 and 6 describe how the unbuilt parts must behave; rule 2 is already how the profession index works inside one process.

A new job is the expensive event, at about 0.15 ms per person in its profession. It happens once per job and off the page's path. Splitting it across workers should shorten it in proportion; that is not measured.

What surrounds the pipeline

  • Settings. Which rules are gates, dimension weights and presets, source precedence, target employers, thresholds, tie-breakers, freshness windows, who may assert what, vocabulary, and per-division overrides are all in one file. Four things are deliberately fixed: every rule runs for every pair, every fact keeps its source, credentials are shown as reported and never as verified, and nothing is sent automatically.
  • Bad data. A missing file, a broken record, an unreadable date or a duplicate never stops matching. Each is worked around, and listed for a person to fix.
  • Names. A stated name is used. Failing that, an email that clearly looks like a name, labelled as such. Failing that, the record id. A guessed name never decides that two records are one person.
  • What to watch in production. Time from event to updated shortlist, queue delay, share of text left unread per source, data problems per source, people moved per event, failed sends. Unread text, data problems and people moved are counted today; the others need the unbuilt parts.
  • A language model, if the client wants one, is a second reader in step 2, behind a guard of ordinary code: a proposal counts only if its quote is word for word in one sentence, mentions the thing outside any understood negation, uses the tool's vocabulary, comes from a document allowed to assert it, and comes from a sentence with no doubt. Disagreement with the rules becomes a question. Paid for once per document. Built and off by default; never run against a real model.
  • The checker (python3 -m shortlist audit) reads every result and confirms the product's own rules hold: tier, score, evidence, authority, doubt, time, action, wording, list order. Clean on the sample, every scenario and with a lying model reader on; a test plants eleven mistakes and each is caught.

Order to build the rest

Each step is useful on its own. More workers come last because the measurements say one process already carries 100,000 people.

  1. Store evidence and claims in a database. A restart stops re-reading every document.
  2. Store rows in a table and read pages from it. Memory no longer grows with open jobs.
  3. Add the queue and one real connector. Replay a real day of events and record the time from event to shortlist.
  4. Add sign-in, the change log and settings versions. The ownership rule can then use the signed-in recruiter.
  5. Add the nightly date event.
  6. Split workers by profession, only if step 3 shows a new job takes too long.

Tied to the sample, and first to revisit with real data: the text reader's 55 rules, the six meanings it recognises in job notes, the vocabulary, and the hand-set weights. A differently worded note is left unread and counted, not misread; a sweep of 124 reworded sentences tests that. The synthetic people measure speed and memory only; they say nothing about match quality.
